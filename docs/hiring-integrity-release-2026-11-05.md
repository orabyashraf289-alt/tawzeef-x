## التحقق المنجز

- TypeScript للواجهة وأدوات Node: ناجح.
- Vitest: **٥٦٤ اختبارًا في ٧٨ ملفًا**، ناجحة.
- بناء نسخة الإنتاج: ناجح. التحذير المتبقي يتعلق بحجم بعض ملفات JavaScript، وتوليد خريطة الموقع استخدم المسار البديل الموجود في المشروع.
- فحص Deno للوظائف الست المعدلة: ناجح باستخدام حزمة Supabase المثبتة محليًا بالإصدار نفسه `2.95.3`. تعذر جلب استيراد CDN مباشرة من بيئة الفحص، لذلك جرى ربطه بالحزمة المحلية للفحص فقط.
- جميع ملفات SQL الجديدة تُجمّع وتنجح اختبارات `supabase/tests/hiring_integrity.sql` في قاعدة PostgreSQL-compatible معزولة عبر PGlite. تختبر صلاحيات الأدوار، رمز المحاولة، ثبات النقاط، الحفظ المتأخر، التصحيح والمراجعة، وارتباط الحجز ومنع التكرار وإعادة الجدولة.
- أضيف تشغيل اختبار SQL نفسه إلى مسار GitHub الذي يعيد تشغيل ترحيلات المشروع على PostgreSQL حقيقي. **يجب أن ينجح هذا الفحص الكامل على طلب الدمج قبل النشر**؛ الفحص المحلي ليس بديلًا عنه.
- جميع البيانات الاصطناعية في اختبار SQL محاطة بمعاملة تنتهي بالتراجع. لم تُضف بيانات تجريبية إلى الإنتاج.

## حدود الحزمة

- ربط الاختبار يعتمد على رمز تتبع الطلب الخاص. ليست هذه إضافة تحقق هوية أو دعوات فردية مستقلة لكل اختبار.
- إذا أغلق المرشح الصفحة، تبقى المهلة محفوظة على الخادم وتُرفض الإجابات المتأخرة؛ يُستكمل إغلاق المحاولة عند عودته وتسليمها. لم تُضف مهمة خلفية دورية لإغلاق الصفحات المتروكة تلقائيًا.
- لم تُجرَّب خدمة التصحيح الحية أو إرسال بريد فعلي في هذه الجولة. إعداد النموذج يدعم `ASSESSMENT_GRADING_MODEL`، والافتراضي يواكب نموذج `gemini-3.8-flash` المستخدم بالفعل في مسارات أخرى بالمشروع. تبقى المراجعة البشرية متاحة عند فشل المزود.
- منع تعارض المقابلات يغطي المقابلات المسجلة داخل المنصة. لم تُضف مزامنة مع تقاويم خارجية. السجلات القديمة التي لا تحدد محاورًا مرتبطًا تستخدم منشئها للتحقق من التعارض، ويُفترض لها توقيت القاهرة ما لم يوجد توقيت محفوظ.
- حراس الصلاحيات يضيفون قيودًا إلى سياسات الوصول الحالية. لا تمثل هذه الحزمة تدقيقًا مكتملًا لكل وظيفة قديمة تستخدم صلاحيات الخدمة أو كل وحدة في النظام.
- يجب التحقق من شاشات الإنتاج بعد نشر الواجهة؛ اكتمال اختبارات الوحدة وحده لا يثبت تجربة الاستخدام الحية.
- يُرفع الكود عبر جلسة GitHub المعتمدة في المتصفح، ثم يُقارن محتوى الفرع مع الملفات المحلية المختبرة قبل الدمج.

## خطوات النشر الجاهزة للتنفيذ

1. رفع الفرع وفتح طلب دمج، ثم نجاح فحوص الواجهة وإعادة تشغيل الترحيلات على PostgreSQL.
2. تطبيق الترحيلات التالية على مشروع Supabase الحالي بالترتيب، دون تشغيل ملف البيانات الاصطناعية على الإنتاج:
   - `20261105080654_hiring_integrity_permissions.sql`
   - `20261105114059_assessment_attempt_integrity.sql`
   - `20261105114802_interview_booking_availability.sql`
3. نشر الوظائف وتبعياتها من نسخة الفرع نفسها: `auto-rank`، `book-interview`، `evaluate-assessment-answers`، `send-assessment-results`، `evaluate-candidate`، `chat`.
4. نشر واجهة الفرع عبر مسار Vercel/GitHub الحالي. تُنسّق خطوات قاعدة البيانات والوظائف والواجهة في نافذة قصيرة؛ واجهة الاختبارات القديمة لن تستطيع استخدام دوال التسليم المتقاعدة.
5. التحقق من نشر النسخة المقصودة ومن أخطاء التشغيل والصلاحيات. اختبار الشاشات بالحساب الصحيح، واستخدام فحوص رفض الطلبات غير المصرح بها دون إضافة طلبات مرشحين أو إرسال رسائل.

عند مشكلة نشر، يُفضّل إصلاح النسخة الجديدة مع إبقاء حماية الدرجات؛ لا تُعاد صلاحيات الدوال القديمة التي تسمح بتسليم غير مرتبط بمحاولة.
